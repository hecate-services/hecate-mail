# PART 3 — Mailboxes

Event-sourced, unlike PART2's directory: a letter's lifecycle (deposited,
read, replied, archived) is a real business process worth an audit trail,
and this workspace's own standing architecture preference is event
sourcing by default for exactly this shape of thing. Uses the `store_id/0`+
`data_dir/0` (+ optional `store_indexes/0`) callbacks `service_anatomy.md`
documents — already generated by this repo's scaffold (`store=1`), so the
`reckon-db` store and its `evoq` subscription are already wired; what
follows is the CMD/PRJ/QRY content on top of that plumbing.

## Aggregate: one stream per citizen's mailbox

```
Stream: mailbox-{citizen_did}
├── letter_deposited_v1   {letter_id, from_did, subject, body, deposited_at}
├── letter_read_v1        {letter_id, read_at}
├── letter_replied_v1     {letter_id, reply_letter_id}
├── letter_archived_v1    {letter_id, archived_at}
```

Same Dossier shape this ecosystem already uses elsewhere
(`capability-mri:...`, `reputation-did:macula:agent123`) — a per-entity
stream, business-verb past-tense events, no CRUD terms anywhere
(`letter_deposited`, not `letter_created`; `letter_read`/`letter_archived`,
not `letter_updated`).

## CMD: `manage_mailboxes`

| Desk | Command | Event |
|---|---|---|
| `deposit_letter/` | `deposit_letter_v1` | `letter_deposited_v1` |
| `mark_letter_read/` | `mark_letter_read_v1` | `letter_read_v1` |
| `reply_to_letter/` | `reply_to_letter_v1` | `letter_replied_v1` (on the *replier's* own outbound reference; the reply itself is a normal `deposit_letter_v1` on the original sender's mailbox) |
| `archive_letter/` | `archive_letter_v1` | `letter_archived_v1` |

Handlers: `maybe_deposit_letter`, `maybe_mark_letter_read`,
`maybe_reply_to_letter`, `maybe_archive_letter` — standard `maybe_*` naming,
each a pure decision over the current aggregate state (e.g.
`maybe_mark_letter_read` refuses if the letter doesn't exist or is already
archived).

`deposit_letter` is exposed as a `capabilities/0` RPC handler directly
(any citizen can attempt to deposit — see the authorization section below
for what's actually checked). `mark_letter_read`/`archive_letter` are
**not** exposed as separate RPCs in v1 — a citizen fetching their own
mailbox (`get_mailbox_by_citizen`, PART3's QRY side) marks-as-read
implicitly as part of the read, collapsing two round trips most clients
would otherwise always do back-to-back into one. Revisit only if a real
client needs to peek without marking read.

## PRJ: projections into a queryable mailbox read model

```
letter_deposited_v1_to_mailboxes
letter_read_v1_to_mailboxes
letter_replied_v1_to_mailboxes
letter_archived_v1_to_mailboxes
```

Storage: `barrel_docdb`, one document per letter, keyed by
`{citizen_did, letter_id}` — consistent with PART2's directory rather than
introducing a second storage engine for one more service; revisit only if
a real query need (e.g. full-text search across letter bodies) turns out
to want something `barrel_docdb` can't do well.

## QRY: `query_mailboxes`

| Desk | Returns |
|---|---|
| `get_mailbox_by_citizen/` | All unarchived letters for a DID, unread first, newest first |
| `get_letter_by_id/` | One letter's full content |

Exposed as `hecate_mail.get_mailbox` / `hecate_mail.get_letter` —
see the authorization section immediately below before treating these as
safe to expose as-is.

## Authorization — an OPEN QUESTION, not a hand-wave

**This is the single most important unresolved item in this whole plan, and
it must be resolved before `get_mailbox`/`get_letter` are exposed for
real, not treated as a detail to sort out while coding.**

`identity_model.md` describes two-sided authorization for a citizen calling
a service: the citizen's own credential proves *"I'm a legitimate realm
citizen,"* and the service's own credential proves *"I'm allowed to answer
for the realm."* Neither of those proves the narrower thing this service
actually needs: *"the citizen calling `get_mailbox` is the SAME citizen who
owns the DID they're asking about."* Realm membership is necessary but not
sufficient — every realm citizen being able to read every other citizen's
mail by knowing their DID would be a real, serious privacy bug, not a
theoretical one.

What isn't yet confirmed from the `hecate_om` guides read for this plan:
**whether a `macula_response:handle_request/2` callback is handed any
cryptographically verified caller identity at all**, versus only the raw
payload the caller chose to send (which a malicious caller could simply
forge — sending someone else's DID as a `from` field proves nothing).
`mesh_native_services.md` mentions `ucan_token` as an option on the
*calling* side (`hecate_om:call_capability/5,7`, for calling a "gated
provider"), which implies gating is possible, but does not show the
*serving* side reading and verifying one inside `handle_request/2`.

**This must be verified against `hecate_om`'s actual source (or asked of
whoever maintains it) before writing `get_mailbox_by_citizen`'s handler —
not assumed either way.** Two honest paths depending on what's actually
there:

1. **If `handle_request/2` (or some `Meta`/`State` alongside it) exposes a
   verified caller cert/DID**: check `caller_did =:= requested_did` inside
   the handler before returning anything, refuse otherwise. This is the
   correct, minimal fix and should be the first thing implemented once
   confirmed available.
2. **If it does not, today**: `get_mailbox`/`get_letter` cannot safely be
   general-purpose `mesh_call`-able RPCs in v1 without *some* proof of
   ownership passed and checked by hand — e.g. requiring the request to
   include a signature over a nonce/timestamp using the same keypair that
   registered the citizen's DID in PART2, verified against the DID's known
   public key. This is real, non-trivial cryptographic plumbing to add
   correctly, and should not be built casually as a stopgap — if this is
   the actual state of things, treat "how a citizen proves ownership of
   their own mailbox" as its own small design question, escalated before
   Phase 2 (PART4) starts, not solved inline while writing the handler.

**Until this is resolved, `deposit_letter` (write-only, no
information disclosure on refusal) is fine to build and ship on its own —
the reader side (`get_mailbox`/`get_letter`) is the part that must wait.**
This ordering is intentional and drives PART4's phase boundaries.

## What "reply" actually means, precisely

A reply is not a new event type on the mailbox stream in the sense of
special-casing the projection — it's an ordinary `deposit_letter_v1` on the
*original sender's* mailbox (found via the letter's own `from_did`, looked
up through PART2's directory exactly like any other deposit), with
`reply_letter_id` cross-referencing the letter being replied to. The
`letter_replied_v1` event exists only on the *replier's own* stream, as a
marker that they've handled it (feeds "unread" logic, nothing more) — it
does not carry the reply's content, the sibling `letter_deposited_v1` on
the recipient's stream does.

## Explicitly not in v1

- **No attachments beyond plain text.** If binary content is ever needed,
  the existing `hecate_om_content:put/1` + `get/1` (content-addressed,
  already wrapped, see PART1's substrate survey) is the right primitive —
  a letter would carry an MCID, not raw bytes, exactly the same shape
  `macula-mcp`'s own `mesh_put`/`mesh_get` already uses. Not built until a
  real need shows up.
- **No read receipts back to the sender.** `letter_read_v1` lives only on
  the recipient's own stream; the sender never learns their letter was
  read unless the recipient replies.
- **No thread/conversation grouping beyond the one-level `reply_letter_id`
  cross-reference.** Multi-message threads are a real feature, deliberately
  deferred rather than half-built.
